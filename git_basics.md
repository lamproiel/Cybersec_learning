## git status
- показывает текущее состояние репозитория - какие файлы изменены, какие добавлены в staging area,
   и какие не отслеживаются Git
- что выводит `git status`
    -  Untacked   #файл существует, но Git его не отслеживает (никогда не был добавлен через `git add`)
    -  Modified   #файл был изменен, но изменения еще не добавлены в staging area
    -  Staged     #файл добавлен в staging ared (через `git add`) и готов к коммиту
    -  Committed  #файл уже закоммичен и не изменялся

## git log 
- посмотреть историю всех коммитов в репозитории - кто, что и когда сохранил
- что выводит `git log`
    -  commit      #уникальный хеш (ID) коммита - a1b2c3d...
    -  Author      #кто сделал коммит (имя и email)
    -  Date        #когда был сделан коммит
    -  Сообщение   #описание изменений (после `-m "..."`
- опции `git log`
    -  `git log --oneline`         #коротко: только хеш и сообщение
    -  `git log -n 3`              #последние 3 коммита
    -  `git log --author="Name"`   #коммиты конкретного автора
    -  `git log --graph --all`     #визуальное дерево веток



# Git Basics (основные комманды) 
## git init
- Инициализирует новый репозиторий Git в текущей папке
- создает скрытую папку `.git`

	-  `.git/`
	-    `objects/`      #папка для хранения объектов (коммиты, файлы и т.д.)
	-    `refs/`         #ссылки на ветки и теги
	-    `heads/` 	    #указатели на локальные ветки
	-    `tags/`         #указатели на теги
	-    `hooks/`        #скрипты, которые выполняются при определённых событиях
	-    `config`        #конфиг репозитория
	-    `description`   #описание репозитория
	-    `HEAD`          #указатель на текущую ветку

- когда использовать `git init`
	-  новый проект (вы начинаете разрабатывать проект с нуля и хотите отслеживать его изменения
	-  существующий проект (у вас уже есть папка с файлами, и вы хотите начать использовать Git)
	-  после клонирования (обычно не нужна - `git clone` уже создает репозиторий)
- пример использования:
	-  `cd my_project`     #перейти в папку проекта
	-  `git init`          #инициализировать репозиторий
	-  `ls -la`            #вы увидите папку `.git`
	-  после этого папка становится Git репозиторием и вы можете:
	-    добавлять файлы командой `git add`
	-    создавать коммиты командой `git commit`
	-    просматривать историю изменений командой `git log`
	-    работать с ветками и удалёнными репозиториями
- важные детали
	-  `git init` создает только локальный репозиторий на вашем компьютере
	-  это не загружает код на удаленный репозиторий (надо юзать `git remote add`, `git push`)
- работа в подпапках
	-  git видит все файлы в текущей папке и во всех вложенных подпапках
	-  не нужно запускать `git init` в каждой подпапке - одного раза в корне проекта достаточно
- опции
	-  `git init my-project`             #создать репозиторий в новой папке my-project
	-  `git init --bare`                 #создать "голый" репозиторий (без рабочей папки)
	-  `git init --initial-branch=main`  #создать реопзиторий с веткой main вместо master

 
## git add
- добавляет файлы в staging area для следующего коммита
	-  `git add <Файл>`
- три состояния файла в git
	-  working directory (ваш диск)
             `git add`
	-  staging srea (подготовка к коммиту)
             `git commit`
	-  repository (история, `.git`)
- пример:
	-  `nano git_basics.md`             #редактировать файл в нано
	-  `git status`			    #файл изменился, но Git его не видит в истории
	-  `git add git_basics.md`	    #добавляете в staging area
	-  `git status`			    #"Changes to be committed"
	-  `git commit -m "Update notes"`   #коммитите (сохраняете в историю)
- опции
	-  `git add git_basics.md`    #добавить один файл
	-  `git add .`                #добавить ВСЕ изменённые файлы
	-  `git add *.md`             #добавить все .md файлы
	-  `git add folder/`          #добавить все файлы в папке


## git commit
- сохрняет файлы в историю Git
- как использовать
	-  `git commit -m "описание изменений"`   #`-m` = message (сообщение)
- пример:
	-  `git add git_basics.md`
	-  `git commit -m "Add git basics notes"`
	-  `git log`


## git push
- отправляет ваши коммиты на удалённый сервер (GitHub, GitLab)
- схема:
	- Ваш компьютер (локальный Git) - Удалённый сервер (GitHub/GitLab)
	- `git add`  - `git commit` - `git push`
	- подготовка    сохранение     отправка
- пример:
	-  ` git push origin main`   #origin - имя удалённого сервера, main - ветка (основная)


## git pull
- скачивает коммиты с удалённого сервера на ваш пк (забрать изменения из репозитория)
- схема:
	- Удалённый сервер (GitHub/GitLab) - Ваш компьютер (локальный Git)
	- пример:
	-  ` git pull origin main`   #скачиваются все новые коммиты с GitHub на ваш пк


## как пушить на гитхаб
- создать репо
- локально настроить Git
	1.  `git remote add origin git@github.com:<ИМЯ>/<НАЗВАНИЕ РЕПО>.git`
	-    #связывает локальный репозиторий с удаленным репозиторием
	-    #`git remote` команда для управления удаленными хранилищами
	-    #`add` добавить новый удаленный репозиторий
	-    #`origin` имя удаленного репо (по умолчанию)
	-    #`git@github.com:<ИМЯ>/<НАЗВАНИЕ РЕПО>.git` SSH адрес моего репо на GitHub

	2.  `git branch -M main`
	-    #переименовывает текущую ветку в main
	-    #`git branch` команда для управления ветками
	-    #`-M` флаг "move" (переименовать) принудительно
	-    #`main` новое имя ветки

	3.  `git push -u origin main`   #`-u` связывает ветку с удалённой - дальше можно просто git push
	-    #отправляет коммиты с локального пк на GitHub и связывает ветку
	-    #`git push` команда для отправки коммитов на удаленный репо
	-    #`u` флаг "upstream" связывает локальную ветку с удаленной
	-    #`origin` имя удаленного репо (куда отправляем)
	-    #`main` имя ветки (что отправляем)

- каждый раз после 
	-  `git add .`             #добавить файлы
	-  `git commit -m "..."`   #сделать коммит
	-  `git push`              #отправить на GitHub


# работа с ветками, тегами 
## ветка (branch) - линия разработки. По умолчанию главная ветка main.
- просмотр веток
	-  `git branch`              #список локальных веток
	-  `git branch -a`           #все ветки (локальные и удалённые)
	-  `git branch -v`           #ветки с последним коммитом
	-  `git branch --merged`     #показать ветки, слитые в текущую
	-  `git branch --no-merged`  #показать ветки, которые ещё не слиты
- создание новой ветки
	-  `git branch feature/new-auth`       #создать ветку (но не переходить в неё)
	-  `git checkout -b feature/new-auth`  #создать и сразу перейти
- переключение между ветками 
	-  `git checkout feature/new-auth`     #переключиться на ветку
- удаление ветки 
	-  `git branch -d feature/new-auth`             #удалить локальную ветку	
	-  `git branch -D feature/new-auth`             #принудительно удалить	
	-  `git push origin --delete feature/new-auth`  #удалить удалённую ветку
- переименование ветки
	-  `git branch -m old-name new-name`   #переименовать локальную ветку
	-  `git push origin -u new-name`       #загрузить с новым именем
	-  `git push origin --delete old-name` #удалить старую на сервере
- слияние веток (merge) объединяет две ветки вместе. Обычный workflow:
	-  `git checkout main`           #переходим на main
	-  `git pull origin main`        #обновляем локальную main
	-  `git merge feature-new-auth`  #сливаем feature в main
	-  `git push origin main`        #загружаем результат
- отправка новой ветки на GitHub (первый раз)	
	-  `git push -u origin feature/new-auth`  #`-u` устанавливает upstream, след. раз `git push`


## теги (tags) - используются для отметки важных моментов в истории проекта, обычно релизы (версии)
- создать тег
	-  `git tag v1.0.0`                   #лёгкий тег
	-  `git tag -a v1.0.0 -m "Release"`   #тег с описанием
- посмотреть теги 
	-  `git tag`           #список всех тегов
	-  `git show v1.0.0`   #информация о теге
- отправить тег на GitHub
	-  `git push origin v1.0.0`      #отправить конкретный тег
	-  `git push origin --tags`      #отправить все теги
- удалить тег
	-  `git tag -d v1.0.0`                 #удалить локально
	-  `git push origin --delete v1.0.0`   #удалить на сервере

# стратегии ветвления (для управления релизами и разработкой)
- стратегия ветвления - это правила, по которыи ведётся разработка в Git

## GitFlow 
### основные ветви
| команда | назначение | откуда создаётся | удаляется после |
|---------|------------|------------------|-----------------|
| `main` | только стабильные релизы (прод) | - | никогда |
| `develop` | интеграция фич перед релизом | `main` | никогда |
| `feature/*` | разработка новых функций | `develop` | слияния в `develop` |
| `release/*` | подготовка к релизу (тест, баги) | `develop` | слияния в `main` и `develop` |
| `hotfix/*` | срочные баги в проде | `main` | слияния в `main` и `develop` |


## GitHub Flow - упрощённая альтернатива Git Flow 
### основные ветви
| команда | назначение |
|---------|------------|
| `main`  | всегда готовый к проду код |
| `feature/* | временные ветви для новых функций или фиксов |



# остальные команды
-  `git checkout` - для переключения между ветвями и восстановления файлов из истории
	-  `git checkout <branch_name>`     #переключиться на существующую ветвь
	-  `git checkout -b <branch_name>`  #создать новую ветвь и переключиться на неё
	-  `git checkout -`                 #вернуться на предыдущую ветвь
-  `git merge` - объединение истории одной ветви в другую (слияние ветвей)
	-  `git checkout main`           #переключиться на целевую ветвь (куда сливаем)
	-  `git pull origin main`        #обновить локальную копию из удалённого репо
	-  `git merge <branch_name>`     #слить ветвь в текущую (main)
	-  `git push origin main`        #отправить изменения на удалённый сервер
-  `git rebase` - переписывание истории коммитов путём перемерещения ветви на новую базу
	-  `git rebase <base_branch>`    #переместить текущую ветвь на вершину `base branch`
	-  `git rebase -1 HEAD~3`        #интерактивный rebase последних 3 коммитов
	-  `git rebase --abort`          #отменить процесс rebase
	-  `git rebase --continue`       #продолжить после разрешения конфликтов
-  `git fetch` - загрузка обновленипй из удалённого репозитория без изменения локальных ветвей
	-  `git fetch origin`            #загрузить все обновления с удалённого репо `origin`
	-  `git fetch origin <branch>`   #загрузить обновления конкретной ветви
	-  `git fetch --all`             #загрузить обновления со всех удалённых репо
	-  `git fetch --prune`           #загрузить и удалить локальные ссылки на удалённые ветви, которые были удалены
-  `git revert` - отмена изменений конкретного коммита путём создания нового коммита
	-  `git revert <commit_hash>`    #отменить коммит, создав новый коммит-отмену
	-  `git revert HEAD`             #отменить последний коммит
	-  `git revert -n <commit_hash>` #отменить коммит n шагов назад
	-  `git revert --continue`       #продолжить после разрешения конфликтов
	-  `git revert --abort`          #отменить операцию revert
-  `git diff` - просмотр различий между версиями файлов
	-  `git diff`                    #сравнить рабочую директорию с индексом (staging area)
	-  `git diff --staged`           #сравнить индекс с последним коммитом
	-  `git diff HEAD`               #сравнить рабочую директорию с последним коммитом
	-  `git diff <commit1> <commit2>`#сравнить два коммита
	-  `git diff <commit> -- <file>` #сравнить конкретный файл
	-  `git diff --name-only`        #показать только имена изменённых файлов
	-  `git diff --stat`             #показать статистику (кол-во изменений)
-  `git clone` - загрузка полной копии удалённого репозитория на локальный компьютер
	-  `git clone <URL>`             #клонировать репозиторий с именем по умолчанию
	-  `git clone <URL> <directory>` #клонировать в папку с кастомным именем
	-  `git clone --depth 1 <URL>`   #клонировать только последний коммит (быстрее)
	-  `git clone --branch <branch> <URL>` #клонировать конкретную ветвь
	-  `git clone --single-branch <URL>`   #клонировать только одну ветвь
	-  `git clone --recursive <URL>`       #клонировать с подмодулями
