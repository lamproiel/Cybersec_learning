# компьютерные сети

## модель TCP/IP: не OSI (это теория), а именно TCP/IP - то, на чём живёт интернет

### 4 слоя TCP/IP
- TCP/IP - 4 слойная модель, которая описывает как устроен инетрнет и как комтьютерны обмениваются
данными. OSI (семиуровненая модель), но TCP/IP проще и практичнее - она описывает именно то, что
реально работает в интернете.

| Слой | Название | Функция | Примеры протоколов | Единица |
|------|----------|---------|--------------------|---------|
| (Application L4) | Прикладной | Взаимодействие с пользователем; правила, по которым приложения общаются | HTTP, HTTPS, DNS, SSH, FTP, SMTP, POP3, IMAP, Telnet, DHCP, NTP | Данные (Data) |
| (Transport L3) | Транспортный | Доставка данных между процессами; управление портами, надёжность | TCP, UDP, SCTP | Сегмент (TCP), датаграмма (UDP) |
| (Internet L2) | Межсетевой | Маршрутизация между сетями; IP-адреса | IP (IPv4, IPv6, ICMP, IGMP) | Пакет (IP Packet) |
| (Network L1) | Канальный | Передача по физической среде; MAC-адреса, соседние устройства | Ethernet, WI-FI (802.11), PPP, ARP | Фрейм (Frame) |

#### прикладной слой (L4)
- прикладной слой - правила, по которым программы обмениваются данными. Браузер и сервер используют
протокол HTTP или HTTPS.
	- HTTPS - это HTTP поверх TLS

- TLS (промежуточный слой) - проверяет сертификат сервера, договаривается о параметрах шифрования и создает ключи,
которыми будут защищаться данные. После TLS браузер отправляет HTTP-запрос, но уже внутри
зашифрованного соединения. Работа TLS ключа:
	- браузер → сервер: "хочу безопасное соединение"
	- сервер → браузер: отправляет сертификат (публичный ключ сервера)
	- браузер: проверяет подпись сертификата, генерирует симметричный ключ
	- браузер → сервер: отправляет симметричный ключ, зашифрованный публичным ключом сервера
	- браузер ↔ сервер: обмен данными симметричным ключом (быстро)
	- после этого весь трафик (HTTP-запросы) идет зашифрованным внутри TLS-тунеля.

- основные протоколы:

| протокол | порт | назначение | работает поверх |
|----------|------|------------|-----------------|
| HTTP | 80 | передача веб-страниц, незашифровано | TCP |
| HTTPS | 443 | HTTP + TLS шифрование | TCP + TLS |
| DNS | 53 | преобразование имен (example.com - 93.184.216.34) | TCP/UDP |
| SSH | 22 | удаленное управление, шифрование | TCP |
| FTP | 21 | передача файлов, незашифровано | TCP |
| SMTP | 25/587 | отправка писем | TCP |
| POP3 | 110 | получение писем (удаляет с сервера) | TCP |
| IMAP | 143 | получение писем (синхронизирует) | TCP |
| Telnet | 23 | удаленное управление, незашифровано | TCP |
| DHCP | 67/68 | выдача IP-адресов в сеть | UDP |
| NTP | 123 | синхронизация времени | UDP |

##### DNS
- Суть: система сопоставления имён ↔ IP-адресов (и других записей).
- Процесс для “обычного” хоста:
	- Браузер просит example.com.
	- Разрешение идёт к DNS resolver’у (обычно рекурсивный сервер провайдера/роутера).
	- Рекурсор либо:
		- отдаёт из кэша,
		- либо делает запросы к вышестоящим серверам по цепочке.
- Клиент получает ответ (A/AAAA, иногда CNAME), и дальше уже ходит по TCP/UDP к IP.
- Почему DNS вектор №1:
	- Это самый первый этап “доставки” (имя → адрес), его часто трогают до любой “прикладной логики”.
	- Влияет на весь дальнейший трафик: подменили ответ DNS → все соединения уходят не туда.
	- DNS имеет множество реализаций/кэшей/оверлапов, и вокруг него исторически много “доверий” (резолверы, forwarding, split-horizon, кеширование).

#### транспортный слой (L3)
- транспортный слой - доставляет данные между конкретными процессами на разных пк через порты
- порты и сокеты
	- порт - конкретный номер сетевого процесса (число 0-65535, идентификатор процесса на машине)
	- сокет - пара (IP-адрес, порт), уникально идентифицирует соединение
		- сокет пк: 192.168.1.20:50021 (50021 - временный порт клиента)
		- сокет сервера: 142.250.190.14:443 (443 - порт HTTPS на сервере, известный, постоянный)
- диапазоны портов:

| диапазон | название | примеры |
|----------|----------|---------|
| 0-1023 | well-known ports | 80 (HTTP), 443 (HTTPS), 22 (SSH), 25 (SMTP) |
| 1024 - 49151 | registred ports | 3306 (MySQL), 5432 (PostgreSQL), 8080 (альтернативый HTTPS) |
| 49152-65535 | ephemeral ports | клиентские временные порты, назначаются OC |
 
- TCP (Transmission control protocol) - надежная доставка потока данных:
	- установление соединения перед передачей данных
	- нумерует части данных (sequence numbers)
	- гарантирует доставку: получатель отправляет подтверждение (ACK)
	- обнаруживает потери и повторно отправляет
	- порядок доставки сохраняется
	- медленнее, чем UDP, но надежнее
- TCP Handshake (трехстороннее рукопожатие)
	- Клиент (192.168.1.20:50021) → Сервер (142.250.190.14:443)
	- SYN: Клиент → Сервер "Хочу соединение. Мой начальный sequence number = X"
	- SYN-ACK: Сервер → Клиент "Принял. Мой sequence number = Y, подтверждаю твой X+1"
	- ACK: Клиент → Сервер "Принял. Подтверждаю твой Y+1"
	- соединение установлено, можно передавать данные
- TCP flags (в заголовке TCP 6 флагов)

| флаг | обозначение | значение |
|------|-------------|----------|
| SYN | synchronize | запрос на соединение (handshake 1 и2) |
| ACK | acknowledgment | подтверждение получения (handshake 3 и далее все сегменты |
| FIN | finish | завершение соединения |
| RST | reset | сброс соединения (ошибка или отказ) |
| PSH | push | немедленно отправить данные приложение (не ждать буферы) |
| URG | urgent | срочные данные (редко) |

- TCP Segment (единица данных TCP)

| поле | размер | назначение |
|------|--------|------------|
| source port number | 2 байта | порт отправителя |
| destination port number | 2 байта | порт получателя |
| seq number | 4 байта | номер первого байта данных в этом сегменте |
| ack | 4 байта | номер след. байта, который отправитель ожидает получить |
| flags | обычно часть заголовка | управляющие признаки: SYN, ACK, FIN, RST и др. |
| data | переменный размер | полезные данные, например HTTP или TLS |
 
- UPD (user datagram protocol) - тоже транспортный протокол, но не устанавливает полноценное соединение и не гарантирует доставку каждой части.
	- нет установления соединения (отправляешь и забываешь)
	- нет гарантии доставки
	- нет подтверждений
	- нет повторных отправок
	- быстрее TCP
	- используется, когда скорость важнее надёжности
- когда UDP:
	- DNS-запросы (быстрые, по одному)
	- Видеотрансляция (потеря пакета не критична)
	- Онлайн-игры (скорость > надёжность)
	- DHCP

#### межсетевой слой (L2)
- межсетевой слой отвечает за IP-адреса и маршрутизацию.
- IPv4-адрес:
	- 32 бита, 4 октета (0-255 каждый)
- маска подсети и CIDR-нотация
	- маска подсети определяет, какая часть IP-адреса - сеть, какая - хост
	- /24 = 24 бита на сеть, 8 бит на хост (8 бит - 1 октет)
	- 192.168.1.0/24 = сеть от 192.168.1.0 до 192.168.1.255 (256 адресов)
		- .0 - адрес сети
		- .1 - .254 - адреса хостов 
		- .255 - broadcast-адрес (отправка всем в сети)
- формула
	- хостов = 2^(32 − маска) − 2
	- 2^(32−24) − 2 = 2^8 − 2 = 256 − 2 = 254 хоста
	- −2: адрес сети и broadcast не используются под хосты
	- IP-адрес 192.168.1.0/24: 24 бита — сеть, 8 бит — хосты. Итого 254 рабочих адреса
- шпаргалка по маскам

| маска | хостов | применение |
|-------|--------|------------|
| /32 | 1 | Конкретный IP (Security Group, /32 route) |
| /30 | 2 | Point-to-point линк между роутерами |
| /28 | 14 | Маленькая подсеть |
| /27 | 30 | Небольшой кластер |
| /26 | 62 | Средняя подсеть |
| /25 | 126 | Половина класса C |
| /24 | 254 | Типичная локальная сеть |
| /22 | 1 022 | Несколько филиалов |
| /16 | 65 534 | Большая корп. сеть |
| /8 | 16 777 214 | Мегаблок (10.0.0.0/8 — RFC 1918) |
	- Формула: 2^(32−маска)−2. /32 — один хост, /0 — весь интернет.
- примеры:

| CIDR | Маска | Хостов | Диапазон |
|------|-------|--------|----------|
| /32 | 255.255.255.255 | 1 | Один адрес |
| /30 | 255.255.255.252 | 2 | Роутер-роутер линк |
| /24 | 255.255.255.0 | 254 | Домашняя сеть |
| /16 | 255.255.0.0 | 65534 | Корпоративная сеть | 
| /8 | 255.0.0.0 | 16777214 | Огромная сеть |

- маршрутизация 
	- пк (192.168.1.20) хочет отправить пакет Гуглу (142.250.190.14)
	- пк проверяет: "142.250.190.14 в моей подсети /24?"
	-  192.168.1.0/24 — нет, не совпадает
	- пк: "Отправляю на роутер (default gateway: 192.168.1.1)"
	- роутер получает IP-пакет
	- извлекает: назначение 142.250.190.14
	- проверяет таблицу маршрутизации: "Куда дальше?"
	- роутер создаёт новый Ethernet-фрейм
	- целевой MAC — следующий роутер провайдера
	- IP-пакет остаётся внутри, не меняется
	- по цепочке: ПК → Домашний роутер → Роутер провайдера → интернет-магистраль → Роутеры по дороге → Гугл
- Таблица маршрутизации роутера:

|------------|------------|
| 10.0.0.0/8 | eth0 |
| 192.168.1.0/24 | eth1 |
| 0.0.0.0/0 |  10.0.0.1 (default route, если не нашли выше) |
	- а каждом хопе IP-адреса остаются теми же, меняются только MAC-адреса в фрейме
- TTL (time to live) - защита от циклов (число в IP-заголовке, ограничивающее время жизни пакета в сети
	- поле в IP-заголовке (8 бит, 0–255)
	- на каждом маршрутизаторе TTL уменьшается на 1
	- если TTL = 0, пакет выбрасывается (и возвращается ICMP сообщение об ошибке)
	- стандартное начальное значение: 64 или 128 (зависит от ОС)
	- для Red Team: утилита traceroute использует TTL для определения пути до сервера
- ICMP (internet control message protocol) - для диагностики сетей, не для передачи данных

| тип ICMP | назначение |
|----------|------------|
| echo request | ping запрос (ты живой?) |
| echo reply | ping ответ (я живой) |
| destination unreachable | маршрут не найден, хост не в сети |
| time exceeded | TTL закончился |
| redirect | используй другой маршрут |
- пример:
	- ping google.com
	- отправляет ICMP Echo Request → получает Echo Reply
	- показывает время отклика (RTT = Round Trip Time)
	- для Red Team: ICMP можно использовать для разведки сети, но современные фаерволы часто блокируют ICMP

#####  ARP  (address resolution protocol) - узнать MAC-адрес устройства по его IP-адресу внутри локальной сети. Хост знает IP, но нужен MAC для отправки Ethernet-кадра. Отправляет
broadcast «У кого IP X?», получатель отвечает своим MAC. Кешируется в ARP-таблице (ip neigh). Протокол L2
	- ПК (192.168.1.20) хочет отправить фрейм роутеру (192.168.1.1), пк  знает IP роутера, но не знает его MAC
	- ПК создаёт ARP-запрос: "Кто имеет IP 192.168.1.1? Отпишитесь с вашим MAC"
	- отправляет broadcast Ethernet-фрейм (MAC destination = FF:FF:FF:FF:FF:FF)
	- все устройства в сети получают, проверяют
	- роутер: "Это обо мне! Мой MAC = 3c:52:82:ab:10:ff"
	- отправляет ARP-ответ
	- пк запоминает: 192.168.1.1 → MAC 3c:52:82:ab:10:ff
	- записывает в ARP-таблицу (кэш, обычно 15–20 минут)
	- теперь ПК создаёт Ethernet-фрейм:
	- MAC destination = 3c:52:82:ab:10:ff
	- внутри IP-пакет с назначением на Гугл 
- команды для проверки:
	- `arp -a`              # показать ARP-таблицу
	- `arp -d 192.168.1.1`  # удалить запись (Linux: `sudo arp -d`)
- для Red Team:
	- ARP spoofing: отправить поддельный ARP-ответ, выдав себя за другое устройство. перехватывать трафик
	- ARP scan: отправить ARP-запросы всем адресам сети → узнать, какие хосты живые
	- ARP poisoning: заполнить ARP-кэш жертвы фальшивыми записями (MITM-атака) 
- инструменты 
	- `arp-scan -l`         # сканировать локальную сеть
	- `arping 192.168.1.1`  # пинг через ARP

##### Gateway (шлюз)
- Gateway в контексте IP — это роутер/узел, который принимает пакеты “не для этой сети”.
- Правило маршрутизации на хосте:
	- Если destination IP в твоей локальной подсети → отправляешь на локальный next-hop (часто напрямую через ARP).
	- Иначе → отправляешь пакетом на default gateway (default route).
	- Хост инкапсулирует/пересылает пакет на MAC-адрес роутера (через ARP к gateway), а дальше роутер уже маршрутизирует в нужную сеть.

##### Traceroute
- Суть: измерение “маршрута по hop’ам” до destination.
- Как обычно работает:
	- Строятся пакеты с разными TTL (Time To Live).
	- Когда TTL у пакета уменьшается до 0 на каком-то роутере, роутер отправляет обратно ICMP message типа Time Exceeded.
	- traceroute показывает список устройств, которые “съедали” TTL на каждом шаге.
- Что важно:
	- Ответы могут быть заблокированы фильтром (ICMP rate-limit/deny) → “ *” на некоторых hop’ах.
- Из-за load-balancing может быть разный маршрут в разные моменты времени.

#### канальный слой (L1)
- канальный слой - передача данных между соседними устройствами в одной локальной сети. Здесь
используются Ethernet-кадры, MAC-адреса, Wi-Fi и правила доступа к среде передачи.
- MAC-адрес
	- 48 бит, 6 октет в шестнадцатеричной системе
	- пример: 3c:52:82:ab:10:ff
	- записан в сетевом интерфейсе (не меняется без перепрограммирования)
	- используется только внутри локальной сети
	- первые 3 октета (OUI) — производитель, последние 3 — уникальный номер
	- например пк хочет отправить пакет серверу гугл. Он не знает MAC-адрес сервера гугл и не
должен его знать. Он отправляет локальный кадр на MAC-адрес домашнего роутера.
	- MAC-адрес - адрес конкретного сетевого интерфейса (Wi-Fi или Ethernet), который записывается
в Wi-Fi кадр. Используется внутри локального сегмента сети. Он помогает передавать Ethernet или Wi-Fi 
кадр ближайшему устройству. MAC-адрес нужен, чтобы Wi-Fi или Ethernet понял: этот кадр предназначен 
именно роутеру, а не другому телефону или компьютеру в домашней сети. Внутри кадра находится IP-пакет
с IP-адресом удалённого сервера. После получения кадра роутер не передает тот же самый Wi-Fi кадр 
дальше в интернет. Он извлекает IP-пакет и создает новый кадр для следующего участка. Обычно записан
в шестнадцатеричном виде: 3с:52:82:ab:10:ff

#### Ethernet frame (структура)
- Ethernet frame - базовая единица передачи данных в сетях Ethernet, она содержит информацию о маршрутизации и типе данных, которые передаются.

| поле | размер | описание |
|------|--------|----------|
| dest MAC (адрес назначения) | 6 байт | MAC-адрес устройства-получателя в локальной сети |
| source MAC (адрес источника) | 6 байт | MAC-адрес устройства-отправителя |
| type/ethertype (тип протокола) | 2 байта | определяет протокол следующего уровня |
| IP packet/TCP (полезная нагрузка) | 46-1500 байт | данные, которые передаются (IP-пакет, TCP-сегмент и тд) |
| FCS (контрольная сумма) | 4 байта | проверка целостности файла |
- распространенные значения ethertype

| значение | протокол | назначение |
|----------|----------|------------|
| 0x0800 | IPv4 | интернет-протокол версии 4 |
| 0x0806 | APR | протокол разрешения адресов (соответствие IP - MAC) |
| 0X86DD | IPv6 | интернет-протокол версии 6 |

- как это работает:
	- dest MAC и source MAC - адреса устройств в одной локальной сети (например пк и маршрутизатор)
	- type указывает, какой протокол использует полезная нагрузка (обычно IPv4)
	- IP packet содержит IP адреса источника и назначения 
	- FCS - циклическая контрольная сумма, которая помогает обнаруживать ошибки при передаче

#### инкапсуляция (упаковка данных)
- инкапсуляция - процесс добавления заголовков каждого уровня модели OSI к данным при передаче вниз по стеку протоколов, каждый уровень оборачивает данные предыдущего уровня в свой заголовок
	- браузер отправляет HTTP-запрос на гугл (example.com:443, HTTPS)
	- HTTP-запрос (прикладной слой, L4) "GET / HTTP/1.1\r\nHost: example.com\r\n..."
	- TLS берёт и шифрует (часть прикладного слоя) результат: TLS Record (зашифрованные данные)
	- TCP добавляет заголовок (Транспортный слой, L3)

||
|----------------------|
| TCP Header (20 байт) |
| Source Port: 50021 |
| Dest Port: 443 |
| Seq, Ack, Flags, ... |
| TLS-зашифрованные данные |
		-  = TCP Segment
	- IP добавляет заголовок (Межсетевой слой, L2)

||
|---------------------|
| IP Header (20 байт) |
| Source IP: 192.168.1.20 |
| Dest IP: 93.184.216.34 |
| TTL: 64, Protocol: TCP (6) |
| TCP Segment (с данными) |
		- = IP Packet
	- Ethernet добавляет заголовок (Канальный слой, L1)

||
|--------------------------|
| Ethernet Header (14 байт) |
| Dest MAC: 3c:52:82:ab:10:ff |
| Source MAC: aa:bb:cc:dd:ee:ff |
| Type: 0x0800 (IPv4) |
| IP Packet (с TCP, с данными) |
		-  = Ethernet Frame
	- Отправляется по кабелю/Wi-Fi (физический уровень)
#### декапсуляция (распаковка на сервере) 
- декапсуляция - это процесс удаления заголовков каждого уровня в обратном порядке при получении данных. Сервер разбирает кадр слой за слоем, проверяя, предназначены ли ему данные 
	- гугл получает ethernet фрейм
	- Ethernet контроллер: "Мой ли MAC? (FF:FF:FF:FF:FF:FF broadcast или мой)"
		- если да → извлекает IP Packet, удаляет Ethernet Header
	- IP-стек: "Мне ли этот пакет? (93.184.216.34 = мой IP)"
		- если да → проверяет TTL, checksum
		- извлекает TCP Segment, удаляет IP Header
	- TCP-стек: "Мне ли этот сегмент? (Dest Port 443 = мой)"
		- если да → проверяет sequence/ack numbers
		- извлекает TLS запись, удаляет TCP Header
	- TLS/SSL-стек: Расшифровывает с приватным ключом
		- передаёт расшифрованные данные HTTP-приложению
	- HTTP-приложение: Парсит "GET / HTTP/1.1..."
		- обрабатывает запрос, готовит ответ
#### специальные типы адресов и сценарии 
- broadcast (FF:FF:FF:FF:FF:FF, MAC)
	- отправить всем в локальной сети
	- пример: DHCP запрос, ARP запрос
- multicast 
	- отправить группе устройств (не всем, не одному)
	- IP адреса: 224.0.0.0/4 (224.0.0.0 - 239.255.255255)
	- пример: потоковое видео, live трансляция
- localhost/loopback
	- IP: 127.0.0.1 (IPv4), ::1 (IPv6)
	- пакеты не уходят в сеть, остаются на машине 
	- используется для тестирования приложений 
- private IP ranges (RFC 1918)

||
|------------|-----------------------------|
| 10.0.0.0/8 | (10.0.0.0 — 10.255.255.255) |
| 172.16.0.0/12 | (172.16.0.0 — 172.31.255.255) |
| 192.168.0.0/16 | (192.168.0.0 — 192.168.255.255) |
	- не маршрутизируются в интернете 
	- используются внутри корпоративных сетей и домов 
- link-local адреса
	- 169.254.0.0/16
	- назначаются автоматически, если нет DHCP-сервера

#### NAT (network address translation)
- NAT - это технология, которая переводит (трансформирует) IP-адреса в сетевых пакетах, позволяя устройствам с приватными IP-адресами взаимодействовать с интернетом через один публичный IP-адрес
- Суть: подмена адреса в IP-заголовке (обычно “внутренний приватный” ⇄ “внешний публичный”).
- Зачем: экономия публичных IPv4 и скрытие внутренней адресации.
	- Типичный сценарий:
		- Внутренний хост: 10.0.0.5 → 8.8.8.8:53
		- Роутер NAT меняет исходный адрес на свой внешний: 203.0.113.10 → 8.8.8.8:53
		- Роутер ведёт таблицу трансляций, чтобы вернуть ответы обратно внутрь.
	- Формально NAT = минимум “изменение IP”, а направление/правила зависят от типа.

- дома 254 устройства, но провайдер выдал 1 IP. Домашний роутер переписывает адреса
	- твой ПК → Яндекс
	- ПК создаёт пакет:
		- Source: 192.168.1.20:50021 (приватный)
		- Dest: 142.250.190.14:443
	- роутер перехватывает и переписывает:
		- Source: 78.12.34.56:5001 (публичный IP провайдера + новый порт)
		- Dest: 142.250.190.14:443
	- запоминает в таблице:
		- 78.12.34.56:5001 → 192.168.1.20:50021
	- яндекс отправляет ответ:
		- Source: 142.250.190.14:443
		- Dest: 78.12.34.56:5001
	- роутер получает, смотрит таблицу:
		- 5001 → 192.168.1.20:50021
	- переписывает обратно:
		- Source: 142.250.190.14:443
		- Dest: 192.168.1.20:50021
	- отправляет твоему ПК
- типы NAT:
	- full cone: любой внешний адрес может отправить пакет на твой внутренний
	- restricted cone: только адреса, с которыми ты уже общался
	- port restricted cone: только адреса и порты, с которыми ты уже общался
	- symmetric: каждое новое соединение - новый порт (самый безопасный)
- для red team: NAT усложняет сканирование и эксплуатацию, но можно использовать port forwarding для доступа

#### PAT (Port Address Translation)
- Суть: разновидность NAT, где подменяют ещё и порт (разные внутренние клиенты могут идти во “внешний IP”, но порты различаются).
- Это обычно то, что называют “NAT” в домашних роутерах.
- Почему нужен PAT:
	- Если бы NAT менял только IP, все клиенты с приватной сети делили бы один внешний (IP) и конфликтовали бы по “куда возвращать”.
	- С PAT роутер делает трансляцию вида:
		- внутреннее: 10.0.0.5:45678
		- внешнее: 203.0.113.10:52311
	- В таблице роутера хранится маппинг “какой внешний порт соответствует какому внутреннему порту”.
	- Точка важности: корректность возврата определяется таблицей состояний (state/conntrack) и таймаутами.
#### Важные эффекты NAT/PAT на сети
	- Нет end-to-end прозрачности IPv4: “внешний мир” видит публичный адрес роутера, а не реальные адреса хостов.
	- Сложнее входящие соединения по умолчанию: входящий из интернета “не знает” куда форвардить, пока не настроены правила (port forwarding / DNAT).
	- Сейчас это часто усугубляется NAT traversal’ом: приложения типа VoIP/игры могут требовать специфических подходов.
	- Формально меняется адрес в IP заголовке и порт в TCP/UDP: поэтому фильтры/IDS могут видеть “не те” исходные адреса.

#### DHCP (dynamic host configuration protocol)
- DHCP - это протокол автоматического назначения IP-адресов и других сетевых параметров устройствам в сети. Вместо того чтобы вручную вводить IP-адрес каждому устройству, DHCP сервер делает это автоматически.
	- задача: автоматически выдать пк в сети IP-адрес
- новый ПК подключился к Wi-Fi:
	- DHCP Discover (broadcast)
		- ПК: "есть ли тут DHCP-сервер?"
		- отправляет на 255.255.255.255:67 (broadcast)
	- DHCP Offer
		- DHCP-сервер (роутер): "Я есть, вот тебе адрес 192.168.1.100"
	- DHCP Request
		- ПК: "Спасибо, я беру 192.168.1.100"
	- DHCP Ack
		- сервер: "Ок, он твой на 24 часа (lease time)"
	- ПК получает:
		- IP адрес: 192.168.1.100
		- Маска подсети: 255.255.255.0
		- Default gateway: 192.168.1.1
		- DNS сервер: 8.8.8.8, 8.8.4.4
		- Lease time: 86400 секунд (1 сутки)
- для read team: 
	- можно поставить поддельный DHCP-сервер, выдать себя как шлюз → MITM
	- инструмент: dhcp3-server, dnsmasq

## инструменты для read team / blue team
### разведка сетей
- сканирование сети (какие хосты живые)
	- `ping 192.168.1.1`
	- `nmap -sn 192.168.1.0/24`

- сканирование портов
	- `nmap -sT 192.168.1.1`         # TCP scan
	- `nmap -sU 192.168.1.1`         # UDP scan
	- `nmap -sS 192.168.1.1`         # Stealth SYN scan

- определение маршрута
	- `traceroute google.com`
	- `tracert google.com` (Windows)
	- `mtr google.com` (лучше, реал-тайм)

- ARP scan
	- `arp-scan -l`
	- `arping 192.168.1.1`

- DNS разведка
	- `dig example.com`
	- `nslookup example.com`
	- `whois example.com`
### анализ трафика 
- перехват пакетов
	- `tcpdump -i eth0 -n`            # Все пакеты
	- `tcpdump -i eth0 tcp port 80`   # Только HTTP
	- `tcpdump -i eth0 'icmp or arp'` # ICMP и ARP

- GUI анализатор
	- wireshark
### проверка сетевых соединений
- активные соединения
	- `netstat -an`
	- `ss -an`              # Новая версия netstat
- какой процесс использует какой порт
	- `lsof -i :80`         # Порт 80
	- `netstat -tulpn`      # Все TCP/UDP с именами процессов
### MITM и spoofing (для lab окружений) 
- ARP Spoofing
	- `arpspoof -i eth0 -t 192.168.1.100 192.168.1.1`
- DNS Spoofing
	- `dnsspoof -i eth0 -f hosts.txt`
- Перенаправление трафика
	- `iptables -t nat -A PREROUTING -i eth0 -j REDIRECT --to-port 8080`
### HTTPS/TLS анализ
- проверить сертификат
	- `openssl s_client -connect example.com:443`
	- `nmap --script ssl-cert example.com`
- перехват HTTPS (Burp Suite, Fiddler, OWASP ZAP)

## важные моменты для Red Team
- Port Scanning: определяем открытые порты, сервисы, версии
- ARP Spoofing: перехватываем трафик локальной сети
- DNS Spoofing: перенаправляем жертву на поддельный сервер
- MITM (Man-in-the-Middle): встаём между клиентом и сервером
- TCP/UDP Flooding: DoS-атака, перегружаем сеть
- IP Spoofing: подделываем source IP (сложнее в современных сетях)
- Packet Crafting: создаём кастомные пакеты (scapy в Python)
- Firewall Evasion: обходим фильтры (фрагментация, туннелирование)
