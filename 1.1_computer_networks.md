# компьютерные сети

## модель TCP/IP: не OSI (это теория), а именно TCP/IP - то, на чём живёт интернет

### 4 слоя TCP/IP
- TCP/IP - 4 слойная модель, которая описывает как устроен инетрнет и как комтьютерны обмениваются
данными. OSI (семиуровненая модель), но TCP/IP проще и практичнее - она описывает именно то, что
реально работает в интернете.

| Слой | Название | Функция | Примеры протоколов | Единица |
|------|----------|---------|--------------------|---------|
| (Application L4) | Прикладной | Взаимодействие с пользователем; правила, по которым приложения общаются | HTTP, HTTPS, DNS, SSH, FTP, SMTP, POP3, IMAP, Telnet, DHCP, NTP | Данные (Data) |
| (Transport L3) | Транспортный | Доставка данных между процессами; управление портами, надёжность | TCP, UDP, SCTP | Сегмент (TCP), датаграмма (UDP) |
| (Internet L2) | Межсетевой | Маршрутизация между сетями; IP-адреса | IP (IPv4, IPv6, ICMP, IGMP) | Пакет (IP Packet) |
| (Network L1) | Канальный | Передача по физической среде; MAC-адреса, соседние устройства | Ethernet, WI-FI (802.11), PPP, ARP | Фрейм (Frame) |

#### прикладной слой
- прикладной слой - правила, по которым программы обмениваются данными. Браузер и сервер используют
протокол HTTP или HTTPS.
	- HTTPS - это HTTP поверх TLS

- TLS (промежуточный слой) - проверяет сертификат сервера, договаривается о параметрах шифрования и создает ключи,
которыми будут защищаться данные. После TLS браузер отправляет HTTP-запрос, но уже внутри
зашифрованного соединения. Работа TLS ключа:
	- браузер → сервер: "хочу безопасное соединение"
	- сервер → браузер: отправляет сертификат (публичный ключ сервера)
	- браузер: проверяет подпись сертификата, генерирует симметричный ключ
	- браузер → сервер: отправляет симметричный ключ, зашифрованный публичным ключом сервера
	- браузер ↔ сервер: обмен данными симметричным ключом (быстро)
	- после этого весь трафик (HTTP-запросы) идет зашифрованным внутри TLS-тунеля.

- основные протоколы:

| протокол | порт | назначение | работает поверх |
|----------|------|------------|-----------------|
| HTTP | 80 | передача веб-страниц, незашифровано | TCP |
| HTTPS | 443 | HTTP + TLS шифрование | TCP + TLS |
| DNS | 53 | преобразование имен (example.com - 93.184.216.34) | TCP/UDP |
| SSH | 22 | удаленное управление, шифрование | TCP |
| FTP | 21 | передача файлов, незашифровано | TCP |
| SMTP | 25/587 | отправка писем | TCP |
| POP3 | 110 | получение писем (удаляет с сервера) | TCP |
| IMAP | 143 | получение писем (синхронизирует) | TCP |
| Telnet | 23 | удаленное управление, незашифровано | TCP |
| DHCP | 67/68 | выдача IP-адресов в сеть | UDP |
| NTP | 123 | синхронизация времени | UDP |

#### транспортный слой
- транспортный слой - доставляет данные между конкретными процессами на разных пк через порты
- порты и сокеты
	- порт - конкретный номер сетевого процесса (число 0-65535, идентификатор процесса на машине)
	- сокет - пара (IP-адрес, порт), уникально идентифицирует соединение
		- сокет пк: 192.168.1.20:50021 (50021 - временный порт клиента)
		- сокет сервера: 142.250.190.14:443 (443 - порт HTTPS на сервере, известный, постоянный)
- диапазоны портов:

| диапазон | название | примеры |
|----------|----------|---------|
| 0-1023 | well-known ports | 80 (HTTP), 443 (HTTPS), 22 (SSH), 25 (SMTP) |
| 1024 - 49151 | registred ports | 3306 (MySQL), 5432 (PostgreSQL), 8080 (альтернативый HTTPS) |
| 49152-65535 | ephemeral ports | клиентские временные порты, назначаются OC |
 
- TCP (Transmission control protocol) - надежная доставка потока данных:
	- установление соединения перед передачей данных
	- нумерует части данных (sequence numbers)
	- гарантирует доставку: получатель отправляет подтверждение (ACK)
	- обнаруживает потери и повторно отправляет
	- порядок доставки сохраняется
	- медленнее, чем UDP, но надежнее
- TCP Handshake (трехстороннее рукопожатие)
	- Клиент (192.168.1.20:50021) → Сервер (142.250.190.14:443)
	- SYN: Клиент → Сервер "Хочу соединение. Мой начальный sequence number = X"
	- SYN-ACK: Сервер → Клиент "Принял. Мой sequence number = Y, подтверждаю твой X+1"
	- ACK: Клиент → Сервер "Принял. Подтверждаю твой Y+1"
	- соединение установлено, можно передавать данные
- TCP flags (в заголовке TCP 6 флагов)

| флаг | обозначение | значение |
|------|-------------|----------|
| SYN | synchronize | запрос на соединение (handshake 1 и2) |
| ACK | acknowledgment | подтверждение получения (handshake 3 и далее все сегменты |
| FIN | finish | завершение соединения |
| RST | reset | сброс соединения (ошибка или отказ) |
| PSH | push | немедленно отправить данные приложение (не ждать буферы) |
| URG | urgent | срочные данные (редко) |

- TCP Segment (единица данных TCP)

| поле | размер | назначение |
|------|--------|------------|
| source port number | 2 байта | порт отправителя |
| destination port number | 2 байта | порт получателя |
| seq number | 4 байта | номер первого байта данных в этом сегменте |
| ack | 4 байта | номер след. байта, который отправитель ожидает получить |
| flags | обычно часть заголовка | управляющие признаки: SYN, ACK, FIN, RST и др. |
| data | переменный размер | полезные данные, например HTTP или TLS |
 
- UPD (user datagram protocol) - тоже транспортный протокол, но не устанавливает полноценное соединение и не гарантирует доставку каждой части.
	- нет установления соединения (отправляешь и забываешь)
	- нет гарантии доставки
	- нет подтверждений
	- нет повторных отправок
	- быстрее TCP
	- используется, когда скорость важнее надёжности
- когда UDP:
	- DNS-запросы (быстрые, по одному)
	- Видеотрансляция (потеря пакета не критична)
	- Онлайн-игры (скорость > надёжность)
	- DHCP

#### межсетевой слой
- межсетевой слой отвечает за IP-адреса и маршрутизацию.
- IPv4-адрес:
	- 32 бита, 4 октета (0-255 каждый)
- маска подсети и CIDR-нотация
	- маска подсети определяет, какая часть IP-адреса - сеть, какая - хост
	- /24 = 24 бита на сеть, 8 бит на хост (8 бит - 1 октет)
	- 192.168.1.0/24 = сеть от 192.168.1.0 до 192.168.1.255 (256 адресов)
		- .0 - адрес сети
		- .1 - .254 - адреса хостов 
		- .255 - broadcast-адрес (отправка всем в сети)
- примеры:

| CIDR | Маска | Хостов | Диапазон |
|------|-------|--------|----------|
| /32 | 255.255.255.255 | 1 | Один адрес |
| /30 | 255.255.255.252 | 2 | Роутер-роутер линк |
| /24 | 255.255.255.0 | 254 | Домашняя сеть |
| /16 | 255.255.0.0 | 65534 | Корпоративная сеть | 
| /8 | 255.0.0.0 | 16777214 | Огромная сеть |

- маршрутизация 
	- пк (192.168.1.20) хочет отправить пакет Гуглу (142.250.190.14)
	- пк проверяет: "142.250.190.14 в моей подсети /24?"
	-  192.168.1.0/24 — нет, не совпадает
	- пк: "Отправляю на роутер (default gateway: 192.168.1.1)"
	- роутер получает IP-пакет
	- извлекает: назначение 142.250.190.14
	- проверяет таблицу маршрутизации: "Куда дальше?"
	- роутер создаёт новый Ethernet-фрейм
	- целевой MAC — следующий роутер провайдера
	- IP-пакет остаётся внутри, не меняется
	- по цепочке: ПК → Домашний роутер → Роутер провайдера → интернет-магистраль → Роутеры по дороге → Гугл
- Таблица маршрутизации роутера:

|------------|------------|
| 10.0.0.0/8 | eth0 |
| 192.168.1.0/24 | eth1 |
| 0.0.0.0/0 |  10.0.0.1 (default route, если не нашли выше) |
	- а каждом хопе IP-адреса остаются теми же, меняются только MAC-адреса в фрейме
- TTL (time to live) - защита от циклов (число в IP-заголовке, ограничивающее время жизни пакета в сети
	- поле в IP-заголовке (8 бит, 0–255)
	- на каждом маршрутизаторе TTL уменьшается на 1
	- если TTL = 0, пакет выбрасывается (и возвращается ICMP сообщение об ошибке)
	- стандартное начальное значение: 64 или 128 (зависит от ОС)
	- для Red Team: утилита traceroute использует TTL для определения пути до сервера
- ICMP (internet control message protocol) - для диагностики сетей, не для передачи данных

| тип ICMP | назначение |
|----------|------------|
| echo request | ping запрос (ты живой?) |
| echo reply | ping ответ (я живой) |
| destination unreachable | маршрут не найден, хост не в сети |
| time exceeded | TTL закончился |
| redirect | используй другой маршрут |
- пример:
	- ping google.com
	- отправляет ICMP Echo Request → получает Echo Reply
	- показывает время отклика (RTT = Round Trip Time)
	- для Red Team: ICMP можно использовать для разведки сети, но современные фаерволы часто блокируют ICMP

- ARP  (address resolution protocol) - узнать MAC-адрес устройства по его IP-адресу внутри локальной сети 
	- ПК (192.168.1.20) хочет отправить фрейм роутеру (192.168.1.1), пк  знает IP роутера, но не знает его MAC
	- ПК создаёт ARP-запрос: "Кто имеет IP 192.168.1.1? Отпишитесь с вашим MAC"
	- отправляет broadcast Ethernet-фрейм (MAC destination = FF:FF:FF:FF:FF:FF)
	- все устройства в сети получают, проверяют
	- роутер: "Это обо мне! Мой MAC = 3c:52:82:ab:10:ff"
	- отправляет ARP-ответ
	- пк запоминает: 192.168.1.1 → MAC 3c:52:82:ab:10:ff
	- записывает в ARP-таблицу (кэш, обычно 15–20 минут)
	- теперь ПК создаёт Ethernet-фрейм:
	- MAC destination = 3c:52:82:ab:10:ff
	- внутри IP-пакет с назначением на Гугл 
- команды для проверки:
	- `arp -a`              # показать ARP-таблицу
	- `arp -d 192.168.1.1`  # удалить запись (Linux: `sudo arp -d`)
- для Red Team:
	- ARP spoofing: отправить поддельный ARP-ответ, выдав себя за другое устройство. перехватывать трафик
	- ARP scan: отправить ARP-запросы всем адресам сети → узнать, какие хосты живые
	- ARP poisoning: заполнить ARP-кэш жертвы фальшивыми записями (MITM-атака) 
- инструменты 
	- `arp-scan -l`         # сканировать локальную сеть
	- `arping 192.168.1.1`  # пинг через ARP

#### канальный слой 
- канальный слой - передача данных между соседними устройствами в одной локальной сети. Здесь
используются Ethernet-кадры, MAC-адреса, Wi-Fi и правила доступа к среде передачи.
- MAC-адрес
	- 48 бит, 6 октет в шестнадцатеричной системе
	- пример: 3c:52:82:ab:10:ff
	- записан в сетевом интерфейсе (не меняется без перепрограммирования)
	- используется только внутри локальной сети
	- первые 3 октета (OUI) — производитель, последние 3 — уникальный номер
	- например пк хочет отправить пакет серверу гугл. Он не знает MAC-адрес сервера гугл и не
должен его знать. Он отправляет локальный кадр на MAC-адрес домашнего роутера.
	- MAC-адрес - адрес конкретного сетевого интерфейса (Wi-Fi или Ethernet), который записывается
в Wi-Fi кадр. Используется внутри локального сегмента сети. Он помогает передавать Ethernet или Wi-Fi 
кадр ближайшему устройству. MAC-адрес нужен, чтобы Wi-Fi или Ethernet понял: этот кадр предназначен 
именно роутеру, а не другому телефону или компьютеру в домашней сети. Внутри кадра находится IP-пакет
с IP-адресом удалённого сервера. После получения кадра роутер не передает тот же самый Wi-Fi кадр 
дальше в интернет. Он извлекает IP-пакет и создает новый кадр для следующего участка. Обычно записан
в шестнадцатеричном виде: 3с:52:82:ab:10:ff

#### Ethernet frame (структура)
