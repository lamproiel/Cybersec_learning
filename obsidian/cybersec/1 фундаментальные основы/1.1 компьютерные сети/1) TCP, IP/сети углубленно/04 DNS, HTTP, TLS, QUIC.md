- Application layer часто дает самые понятные артефакты. Но здесь же легко начать додумывать больше, чем реально видно.

- DNS может показывать намерение. HTTP может показывать запрос. TLS может скрыть содержимое, но оставить метаданные.

## DNS 

- DNS часто идет перед основным соединением, поэтому его надо смотреть рано.

- показать DNS:
	`tshark -r traffic.pcapng -Y "dns"`

- вытащить queries:
	- DNS queries — это запросы, которые клиент отправляет на DNS-сервер для получения информации о доменных именах.
	`tshark -r traffic.pcapng -Y "dns.flags.response == 0" -T fields -e frame.time -e ip.src -e dns.qry.name -e dns.qry.type`

- вытащить ответы:
	`tshark -r traffic.pcapng -Y "dns.flags.response == 1" -T fields -e frame.time -e ip.src -e dns.a -e dns.aaaa -e dns.resp.ttl`

### что смотреть в DNS:

1. кто спрашивал
2. кого спрашивал
3. какой resolver отвечал
	- DNS resolver — это программа или сервис, который отправляет DNS queries и разрешает доменные имена в IP-адреса.
4. какие домены были
5. какой qtype
	- QTYPE — это указание, какой именно тип информации вы ищете о домене (адрес, почта, имя и т.д.).
6. какой TTL
7. был ли NXDOMAIN
	- NXDOMAIN (Non-Existent Domain) — это код ответа DNS сервера, который означает, что запрашиваемый домен не существует.
8. были ли CNAME
	- CNAME — это "переадресация" на другой домен вместо прямого IP адреса.
9. совпадает ли ответ с последующим IP-трафиком
10. есть ли подозрительная повторяемость
11. есть ли длинные или энтропийные subdomain
	- Subdomain — это часть доменного имени, которая находится перед основным доменом.

- DNS-запрос сам по себе не доказывает, что соединение потом было. Он только показывает, что кто-то пытался резовлить имя.

### DNS и ИБ

- DNS полезен для:
	- поиска инфраструктуры;
	- malware/beaconing-гипотез;
		- Beaconing — это когда инфицированная машина отправляет периодические сигналы ("маячки") на сервер злоумышленника для получения команд или отчёта о статусе.
	- DNS tunneling признаков;
	- CTF-decoy;
	- восстановления таймлайна;
	- понимания, почему host пошел к конкретному IP.

- Аккуратная формулировка:
	- Fact: host сделал DNS query для example.com.
	- Fact: resolver вернул 93.184.216.34.
	- Probable: последующее TCP-соединение к 93.184.216.34 связано с этим query.
	- Unknown: точный URL, если нет HTTP или proxy-логов.

## HTTP

- HTTP удобен, если он без TLS. Можно видеть method, URI, headers, status code, body.
	- method - действие, которое клиент хочет выполнить с ресурсом.
	- IRU - путь и параметры запроса к ресурсу на сервере
	- headers - метаданные о запросе/ответе (информация о клиенте, кодировке, авторизации).
	- status code - ответ сервера о результате запроса.
	- body - Основные данные, отправляемые или получаемые (JSON, XML, бинарные данные).

- фильтр:
	`tshark -r traffic.pcapng -Y "http.request"`

- поля:
	`tshark -r traffic.pcapng -Y "http.request" -T fields -e frame.time -e ip.src -e http.host -e http.request.method -e http.request.uri -e http.user_agent`

- что смотреть:
	- Host - на какой сервер отправляется beacon.
	- method - какое действие выполняется (GET, POST, PUT, DELETE).
	- URI - путь запроса и параметры.
	- status code - какой ответ дал сервер.
	- User-Agent - какой браузер отправляет запрос.
	- cookies - идентификаторы сессии и bot-specific данные.
		- Beacon host = сервер Command & Control (C&C), на который отправляют отчёты инфицированные машины (боты).
	- authorization headers - токены, credentials и bot-specific authorization.
	- content type - тип данных в теле запроса/ответа.
	- body length - размер данных - одинаковый или варьируется?
	- direction - какое направление трафика?
	- timing - периодичность и интервалы между beacon запросами.

- секреты, токены и cookies в pcap лучше не публиковать как есть. В райтапе обычно достаточно показать, что они были найдены, и замаскировать чувствительные части.

## TLS

- TLS шифрует application data. Но не весь контекст исчезает.

- без расшифровки часто остаются:
	- IP
	- port
	- SNI, если виден
		- Это расширение TLS, которое позволяет клиенту сказать серверу, к какому именно домену он подключается, ещё до начала шифрования.  
	- ALPN
		- Это расширение TLS, которое позволяет клиенту и серверу договориться, какой прикладной протокол использовать внутри защищённого соединения ещё во время TLS-handshake.
	- certificate metadata
		- Certificate metadata — это данные из TLS-сертификата, не сам секретный трафик.
	- размеры пакетов
	- timing
		- Timing — это временные признаки соединения: когда начался handshake, сколько длились паузы, как часто идут пакеты, есть ли повторные попытки, и как быстро сервер отвечает.
	- частота соединений
	- направление

- фильтр SNI:
	`tshark -r traffic.pcapng -Y "tls.handshake.extensions_server_name" -T fields -e frame.time -e ip.src -e tls.handshake.extensions_server_name`

- если виден только SNI, значит виден только SNI. Нельзя честно утверджать полный URL или содержимое запроса.

## TLS decryption

- TLS decryption — это расшифровка TLS-трафика, чтобы увидеть содержимое HTTPS-соединения: запросы, ответы, заголовки, иногда тела сообщений.

- Wireshark умеет использовать key log file, например из переменной:
	`SSLKEYLOGFILE=/tmp/keys.log`

- это полезно для своих лабораторий и легального анализа своего трафика. В чужом трафике без ключей содержимое TLS обычно недоступно.

## QUIC и HTTP/3 коротко

- QUIC — это транспортный протокол поверх UDP, который ускоряет и упрощает соединения. 
- HTTP/3 — это HTTP, работающий поверх QUIC вместо TCP. Главная идея: меньше задержек, быстрее установка соединения, лучше поведение при потере пакетов.

- QUIC меняет привычную картину. Это транспорт поверх UDP, и внутри него свой handshake, который совмещает транспортный и TLS 1.3 handshake в одном обмене. Поэтому классического TCP SYN, SYN/ACK, ACK для HTTP/3 не будет, и это нормально, а не повод думать, что capture неполный.
	- capture - запись сетевого трафика для анализа.

- tshark разбирает QUIC из коробки:
	`tshark -r traffic.pcapng -Y "quic"`

- первый пакет QUIC, Initial, шифруется ключами, которые выводятся из версии протокола и connection ID, а не из секретов конкретной сессии. Сделано специально, чтобы такие пакеты мог разобрать кто угодно. Из-за этого Wireshark спозоен показать TLS ClientHello внутри QUIC Initial, включая SNI, без SSLKEYLOGFILE.
	`quic && tls.handshake.extensions_server_name`

- все, что идет после Initial, шифруется уже обычными session keys и без них недоступно, как и в классическом TLS.

- для анализа это значит, что UDP на 443 порту с признаками QUIC надо разбирать отдельно от просто UDP, и не искать там TCP handhsake, которого там не будет.
