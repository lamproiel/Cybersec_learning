
# лаба 1. DNS tunneling своими руками

ставим iodine, если хочется потрогать настоящий инструмент, либо просто эмулируем паттерн через dig, чтобы увидеть сигнатуру в трафике без поднятия туннеля целиком.

терминал 1:
	`sudo tcpdump -ni any udp port 53`

терминал 2, эмулируем "тоннелированные" запросы вручную:
	```
	for i in $(seq 1 20); do
	  chunk=$(head -c 30 /dev/urandom | base32 | tr -d '=' | tr 'A-Z' 'a-z')
	  dig ${chunk}.example.com TXT +short
	  sleep 0.3
	done
	```
смотреть в capture:
- длина subdomain-метки (домен пол 60 знаков)
- похожа ли метка на человекочитаемое имя (нет, закодированные данные)
- как часто идут запросы к одному и тому же домену (20 запросов за 8 сек)
- какой query type преобладает (TXT)

ориентир: обычные пользовательские DNS-запросы короткие и осмысленные, mail.google.com, cdn.example.org. Метка длиной под 50-60 символов из случайных base32/base64-символов, да еще повторяющайся десятками раз подряд к одному домену, статистически выделяется моментально, даже без знания, что это iodine или dnscat2 конкретно.

# лаба 4. Beacon с jitter своими руками

небольшой скрипт, который эмулирует C2-подобный паттерн, чтобы потом его же и детектить.

```python
import time, random, requests

BASE_SLEEP = 5
JITTER = 0.3

while True:
    try:
        requests.get("http://localhost:8000/", timeout=2)
    except Exception:
        pass
    delay = BASE_SLEEP * (1 + random.uniform(-JITTER, JITTER))
    time.sleep(delay)
```

поднять простой HTTP-сервер локально (`python3 -m http.server 8000`), запустить скрипт, снять трафик:
	`sudo tcpdump -ni lo tcp port 8000 -w beacon.pcapng`

дать покрутиться минут пять-десять, потом посчитать интервалы между запросами через tshark:
	`tshark -r beacon.pcapng -Y "tcp.flags.syn==1 && tcp.flags.ack==0" -T fields -e frame.time_relative`

взять получившийся список таймстампов и посчитать разницу между соседними значениями, например в питоне или просто в экселе. Посмотреть на среднее и стандартное отклонение.

ориентир: даже с jitter 30% разброс интервалов остается довольно узким и центрированным вокруг заданного sleep. На реальном трафике человека, листающего сайт, интервалы между запросами куда более рваные и не имеют такого явного центра распределения. Это ровно тот принцип, который лежит в главе beacon-детекта в главе 16.
