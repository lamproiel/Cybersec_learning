- L3 отвечает за доставку между сетями. Здесь уже появляются IP-адреса, подсети, gateway, routing table, TTL, ICMP, MTU и фрагментация.

- На словах это выглядит просто. На парктике ломается на нескольких интерфейсах, NAT, VPN, policy routing, туннелях и неполных capture.

## IP-адрес без маски почти бесполезен

- адрес:
	- `192.168.1.50` сам по себе говорит мало.

- адрес с префиксом: 
	- `192.168.1.50/24` уже говорит, что локальная сеть для хоста примерно такая:
	- `192.168.1.0` - `192.168.1.255`

- если destination внутри этой сети, хост попробует найти MAC через ARP.

- если destination вне этой сети, хост пойдет через gateway.
	- Destination — это адрес назначения, то есть устройство или узел, которому отправляется пакет.

## Longest prefix match

- Routing выбирает маршрут не "первый красивый", а наиболее специфичный по префиксу.

- пример:
	- `default via 192.168.1.1 dev eth0`
	- `10.0.0.0/8 via 192.168.1.254 dev eth0`
	- `10.10.10.0/24 dev tun0`

- для `10.10.10.5` победит /24, потому что он точнее, чем /8
- для `10.20.1.1` победит /8
- для `1.1.1.1` сработает default route

- команда, которую стоит использовать чаще:
	- `ip route get 10.10.10.5` она показываеть, какой route реально выбирает ядро.

## Source address selection

- если у машины несколько адресов, вожно понять, какой source IP будет выбран. 
	- `ip route get 8.8.8.8`

- вывод может показать что то вроде:
	- `8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.50`

- src здесь очень важен. Иногда проблема не в destination, а в том, что система выбирает не тот source address.

## Policy routing

- обычная routing table не всегда единственная. В linux может быть policy routing.
	- Policy Routing (маршрутизация на основе политик) — это метод маршрутизации, при котором пакеты направляются не только на основе адреса назначения, но и на основе других критериев (политик).

- проверка
	- `ip rule`
	- `ip route show table main`
	- `ip route show table all`

- это важно для VPN, containers, multi-homed hosts, lab-сетей и странных CTF-образов.

## Gateway

- Gateway должен быть достижим локально. ТО есть до gateway нужен L2-доступ.

- если gateway указан, но ARP до него не работает, пакеты наружу не пойдут.

- проверки
	- `ip route`
	- `ip neigh`
	- `ping -c 3 <gateway-ip>`

- если ip neigh показывает FAILED, не надо сразу дебажить HTTP. Сначала надо понять L2.

## TTL 

- TTL уменьшается на каждом router hop.

- когда TTL становится 0, router дропает пакет и может отправить ICMP Time Exceeded.

- на этом работает traceroute
	- `traceroute 1.1.1.1`
	- `mtr 1.1.1.1`

- в анализе TTL может подсказать:
	- примерное расстояние;
	- разные сетевые пути;
	- routing loop;
	- подмену ответов;
	- отличие ответа от ожидаемого endpoint.

## ICMP

- ICMP это не только ping

- полезные типы:
	- Echo Request / Echo Reply - ping запрос / ping ответ
	- Destination Unreachable - маршрут не найден, хост не в сети
	- Time Exceeded - TTL закончился
	- Fragmentation Needed - слишком большой пакет, а разделять запрещено
	- Redirect - используй другой маршрут

- ICMP могут фильтровать. Поэтому "ping не идет" не равно "хост мертв".

- но ICMP в pcap часто дает сильные подсказки: кто что не смог доставить, где TTL закончился, где нужен меньший MTU.

## ICMPv6 коротко

- у IPv6 свой ICMP, ICMPv6, и обязанностей у него больше. Туда же входит NDP из главы 01.

- полезные типы:
	- 1   - Destination Unreachable
	- 2   - Packet Too Big
	- 3   - Time Exceeded
	- 128 - Echo Request
	- 129 - Echo Reply
	- 133 - Router Solicitation
	- 134 - Router Advertisement
	- 135 - Neighbor Solicitation
	- 136 - Neighbor Advertisement

- Packet Too Big это аналог Fragmentation Needed из ICMPv4, и для IPv6 он важнее, почему, см. ниже про фрагментацию.

## MTU и PMTUD

- MTU - это максимальный размер пакета, который можно передать без фрагментации на данном участке.

- обычный Ethernet MTU часто 1500.

- туннели добавляют overhead. GRE, VXLAN, WireGuard, IPsec - все это сьедает место. Иногда маленькие пакеты работают, а большие ломаются. Это классический запах MTU-проблемы.

- Path MTU Discovery пытается найти нормальный размер через ICMP Fragmentation Needed. Если ICMP режется firewall, могут появиться странные зависания.

## IPv4 fragmentation

- IPv4-пакет может быть разбит на фрагменты.

- важные поля:
	- Identification
	- Fragment Offset
	- More Fragments
	- Don't Fragment
	- Total Length

- фильтр:
	- `tshark -r traffic.pcapng -Y "ip.flags.mf == 1 || ip.frag_offset > 0"`

- в wireshark: 
	- `ip.flags.mf == 1 || ip.frag_offset > 0`

## Почему fragmentation важна в pcap

- Payload может быть разбит. Если смотреть только в один кадр или просто запускать strings, можно потерять смысл.
	- Payload — это полезная нагрузка пакета, то есть данные, которые пакет реально переносит.

- для CTF это нормальная механика, если она завязана на сетевую логику, а не просто "запихнули флаг в странное место".

- хороший разбор должен учитывать:
	- Есть ли фрагменты?
	- Кто их отправил?
	- Одинаковый ли Identification?
	- Правильный ли порядок offset?
	- Собирается ли payload после reassembly?
	- Есть ли похожий нефрагментированный decoy?

## Фрагментация в IPv6 устроена иначе

- в IPv6 промежуточные роутеры не фрагментируют пакеты вообще. Если фрагментация нужна, ее делает только хост-отправитель, через extension header Fragment Header, а роутеры по пути просто дропают то, что не проходит по MTU, и шлют ответ в ICMPv6 Packet Too big.

- если в сети режут ICMPv6 целиком, PMTUD для IPv6 ломается сильнее, чем для IPv4: источник не получает обратной связи и продолжает слать пакеты, которые не доходят. Поэтому фильтровать весь ICMPv6 на firewall обычно плохая идея, даже если кажется, что это просто пинги.
	- PMTUD — Path MTU Discovery, или определение максимального размера пакета по всему маршруту.
