# Лаба 2. Поймать ARP и NDP


## ARP IPv4

терминал 1:
	`sudo tcpdump -ni any arp`

терминал 2:
	`sudo ip neigh flush all`
	`ping -c 1 1.1.1.1`

смотреть: 
- кто отправил ARP request
- кого он искал
- кто ответил
- какая запись появилась в ip neigh

ориентир: ARP request должен уйти раньше, чем что-либо ответит на ping. Если ARP в capture вообще нет, запись уже была в кэше и flush не сработал, или слушаешь не тот интерфейс.

## NDP IPv6

теперь то же самое для IPv6. Если в этой сети IPv6 вообще нет, считай пункт пропущенным, не везде его раздают.

терминал 1:
	`sudo tcpdump -ni any icmp6`

терминал 2:
	`sudo ip -6 neigh flush all`
	`ping6 -c 1 <IPv6-адрес соседа в сегменте, например gateway из ip -6 route>`

смотреть:
- кто отправил Neighbor Solicitation
- на какой multicast адрес ушел запрос
- кто ответил Neighbor Advertisement
- что появилось в ip -6 neigh

ориентир: вместо broadcast тут multicast на socilited-node адрес, а механика, запрос, ответ, запись в таблице такая же, как в IPv4, просто названия сообщений другие.


# Лаба 3. TCP handshake

терминал 1:
	`sudo tcpdump -ni any tcp port 80 or tcp port 443`

терминал 2:
	`curl -I https://example.com`

искать:
- SYN  (S)
- SYN/ACK  (S.)
- ACK  (.)
- TLS handshake  (P.)
- FIN или RST  (F. / R.)

ориентир: между финальным ACK хендшейка и началом TLS handshake обычно почти нет паузы. Если там заметный разрыв или ретрансмиты, это уже повод смотреть на сеть, а не на сайт.


# Лаба 4. DNS

терминал 1:
	`sudo tcpdump -ni any udp port 53 or tcp port 53`

терминал 2:
	`dig example.com`

ответить:
- какой resolver получил query
- какой qtype был
- какие ответы вернулись
- какой TTL

ориентир: TTL в ответе это не время жизни пакета, это время, на которое резолверу разрешено закэшировать запись. Маленький TTL у домена сам по себе не аномалия, у CDN и balancing-схем это обычное дело.


# Лаба 5. два namespace и veth

Network Namespace - это полностью изолированная копия сетевого стека внутри одного ядра Linux

veth - это виртуальный патч-корд (кабель), у которого всегда ровно два конца (`peer`).

`sudo ip netns add ns1`
`sudo ip netns add ns2`

`sudo ip link add veth1 type veth peer name veth2`

`sudo ip link set veth1 netns ns1`
`sudo ip link set veth2 netns ns2`

`sudo ip netns exec ns1 ip addr add 10.10.10.1/24 dev veth1`
`sudo ip netns exec ns2 ip addr add 10.10.10.2/24 dev veth2`

`sudo ip netns exec ns1 ip link set veth1 up`
`sudo ip netns exec ns2 ip link set veth2 up`
`sudo ip netns exec ns1 ip link set lo up`
`sudo ip netns exec ns2 ip link set lo up`

`sudo ip netns exec ns1 ping -c 3 10.10.10.2`

посмотреть трафик (терминал 1):
	`sudo ip netns exec ns1 tcpdump -ni veth1`

удалить:
	`sudo ip netns del ns1`
	`sudo ip netns del ns2`

разобраться: 
- почему ns1 и ns2 видят друг друга
- где появляется ARP
- что показывает ip neigh внутри ns1
- почему без route в другие сети они не ходят

ориентир: ARP появится даже на прямом veth-линке, потому что L2 есть всегда, IP тут не главный. А до сетей за пределами этой пары пакеты не пойдут именно потому, что неоткуда взяться route, а не из-за firewall.

# лаба 6. маленький pcap-разбор

возьми любой pcap и пройти команды:
1. `capinfos file.pcapng`
	- время начала и конца записи, длительность, сколько всего пакетов и байт, средняя скорость передачи.
2. `tshark -r file.pcapng -q -z io,phs`
	- процентное соотношение протоколов (например, сколько % занимает TCP, UDP, DNS, TLS, ARP и тд)
3. `tshark -r file.pcapng -q -z endpoints,ip`
	- кто передал больше всех пакетов/байт, какие адреса локальные (например 192.168.x.x), какие внешние
4. `tshark -r file.pcapng -q -z conv,ip`
	- между какими конкретно узлами шел основной трафик
5. `tshark -r file.pcapng -Y "arp || dns || icmp || tcp || udp"`
	- конкретные DNS-серверы запросы (какие домены резоливлись), TCP SYN/ACK (попытки подключений), ICMP пинги и тд

	3. сколько адресов (публичных/внешних), объем данных, обмен пакетами
	4. сколько соединений, длительность, сколько пакетов, направление
