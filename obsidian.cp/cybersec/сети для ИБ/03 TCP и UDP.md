- TCP и UDP это место, где появляются порты, соединения, состояния, сканы, reset-пакеты, retransmission и много признаков, полезных для ИБ.

## UDP

- UDP не устанавливает соединение. Пакет отправился, дальше уже как повезет.

- UDP используют:
	- DNS
	- DHCP
	- NTP
	- QUIC
		- QUIC — это современный сетевой протокол передачи данных, который работает поверх UDP.
	- WireGuard
		- WireGuard — это современный VPN-протокол и одновременно набор сетевых механизмов для создания защищённого туннеля между устройствами.
	- некоторые игровые протоколы
	- discovery-протоколы
	- часть C2 и tunneling-сценариев

- В UDP меньше явного состояния, поэтому анализ часто строится на timing, размере пакетов, повторяемости, direction и application layer.
- Отсутствие ответа в UDP можно трактовать только аккуратно:
	- пакет мог быть потерян
	- firewall мог дропнуть
	- сервис мог проигнорировать
	- ICMP error мог быть отфильтрован
	- capture мог быть снят не там

## TCP

- TCP устанавливает соединение.

- классический handshake:
	- client -> server: SYN
	- server -> client: SYN/ACK
	- client -> server: ACK

- после этого идут данные.

- закрытие может быть мягким через FIN или резким через RST.
	- FIN и RST — это флаги TCP протокола, используемые для управления состоянием соединения.
		- FIN означает "завершение соединения" — инициирует корректное закрытие TCP соединения.
		- RST означает "сброс соединения" — принудительное и неожиданное разрыв TCP соединения.

## что смотреть в TCP-потоке

1. Кто отправил SYN?
2. Был ли SYN/ACK?
3. Был ли финальный ACK?
4. Когда пошел payload?
	- Payload (полезная нагрузка) — это данные, которые переносятся в пакете сетевого протокола.
5. Были ли retransmission?
	- Retransmission — это переотправка потерянных пакетов, когда отправитель не получает подтверждение (ACK) в течение определённого времени.
6. Был ли RST?
7. Кто первым закрыл соединение?
8. Есть ли asymmetric routing?
	- Asymmetric Routing (Асимметричная маршрутизация) — это когда пакеты, отправленные от хоста A к хосту B, идут по одному пути, а ответные пакеты от B к A идут по совершенно другому пути через разные маршрутизаторы/сети.
9. Не выглядит ли capture неполным?
	- Packet Capture (Захват пакетов) — это запись сетевого трафика между хостами для анализа, отладки и обнаружения угроз.

- фильтры:
	`tshark -r traffic.pcapng -Y "tcp.flags.syn == 1"`
	`tshark -r traffic.pcapng -Y "tcp.flags.reset == 1"`
	`tshark -r traffic.pcapng -Y "tcp.analysis.retransmission"`

- Wireshark:
	`tcp.flags.syn == 1`
	`tcp.flags.reset == 1`
	`tcp.analysis.retransmission`

## Sequence и ACK

- Sequence (SEQ) и ACK — это номера в TCP заголовке, которые обеспечивают надёжную доставку данных и гарантируют правильный порядок пакетов.

	- SEQ — это порядковый номер байта, который отправляется в этом пакете.
		- Начинается с случайного значения (для безопасности)
		- Увеличивается на количество данных в payload
		- Помогает получателю реконструировать данные в правильном порядке
		
	- ACK — это номер, который говорит: "Я получил все байты до этого номера"
		- Подтверждает получение данных
		- Устанавливается на SEQ + размер payload предыдущего пакета
		- Если данных нет (флаг SYN), то ACK = SEQ + 1

- TCP sequence nummers описывает порядок байтов в потоке.

- ACK говорит, какие байты сторона уже получила.

- для базового анализа не всегда надо вручную считать sequence, но иногда это полезно:
	- при retransmission;
	- при странных RST;
	- при injection;
		- Injection — это класс атак, когда злоумышленник подсовывает программе данные так, что они начинают восприниматься как команды, запросы или код.
	- при неполном capture;
	- при анализе TCP stream.

- Wireshark по умолчанию показывает relative sequence numbers, чтобы было проще читать поток.

## Window

- TCP Window (окно TCP) — это размер буфера, который сообщает отправителю: "Я могу принять столько-то байт, не требуя подтверждения".
	- Управляет потоком данных между отправителем и получателем.

- TCP window показывает, сколько данных получатель готов принять

- проблемы с window могут выглядеть как тормоза, зависания, zero window, повторные попытки.

- фильтры:
	`tcp.analysis.zero_window`
	`tcp.analysis.window_full`

## TCP options

- TCP Options — это дополнительное поле в TCP заголовке для расширенной функциональности помимо базовых полей.
	- Максимальная длина заголовка TCP: 60 байт (базовый заголовок 20 байт + options до 40 байт).

- В заголовке TCP кроме портов и флагов есть options, и часть из них устоит уметь узнавать в pcap.

	- MSS - maximum segment size, согласовывается на handshake
	- Window Scale - множитель для window, без него window ограничен 65535
	- SACK Permitted - сторона умеет selective ACK
	- Timestamps - метки для RTT и защиты от старых дубликатов сегментов

- Options выставляются на SYN и SYN/ACK и дальше держатся на весь коннект. Набор и порядок options, плюс начальный window size и TTL, по сути TCP/IP fingerprint: по ним можно грубо угадывать OS или стек, из которого ушел пакет. Это не точная наука, но как Probable-гипотеза работает неплохо.

- Wireshark:
	`tcp.options.mss_val`
	`tcp.options.wscale.shift`

## RST

- RST означает сброс соединения. Но не всегда его отправляет тот, кого то считаешь конечным сервисом.

- RST может прийти от:
	- реального endpoint;
	- firewall;
	- middlebox;
	- kernel локальной машины;
	- прокси;
	- устройства по пути.

- чтобы не ошибиться, надо смотреть:
	- source IP
	- TTL
	- MAC-контекст
	- sequence number
	- предыдущее состояние соединения
	- timing

## Scan-поведение

- очень грубо:
	- SYN -> SYN/ACK -> порт открыт
	- SYN -> RST          -> порт закрыт
	- SYN -> silence     -> filtered, loss или capture не видит ответ

- но это только базовая модель. В реальности firewall, NAT, IPS и прокси могут менять картину.

## UDP scan

- UDP scan сложнее читать:
	- ответ от сервиса          -> порт вероятно открыт
	- ICMP port unreachable -> порт закрыт
	- нет ответа                      -> open|filtered, loss или фильтрация

- тут особенно нельзя делать слишком уверенные выводы по одному признаку.
